## A. 根因与定性（真实数据核实）

本单覆盖 attempt-1 定位的 C1（4 文件 3 用例）+ C2（5 文件 9 用例）合并秒精度专项，全部同属 06B 缺陷3 根因家族在清理/来源/流水线/克隆域的未覆盖残留。

**C2 — no-op UPDATE → StaleDataError（真生产 bug）：**
真 MySQL 无 `CLIENT_FOUND_ROWS`（生产 `create_engine(mysql+pymysql)` 同语义，SQLAlchemy `dialects/mysql/pymysql.py` connect args 透传、不注入 FOUND_ROWS），幂等/重放/心跳路径在业务字段收敛后仍无条件 `op.updated_at = now()`，单列/整行 UPDATE 命中行但 SET 值四舍五入到与库内相同整秒 → `affected_rows=0` → ORM `check_rowcount` 抛 `StaleDataError`。SQLite 恒返回 1 遮坑。**用 SQL A/B 探针实证**（无 FOUND_ROWS=0 / 有=1），并**推翻 attempt-1 中 codex「已设 FOUND_ROWS」旧结论**。

**C1 — 读回秒精度 / 同秒并列（app 健壮性缺陷）：**
`deleted_at` 写内存微秒、二次读库整秒 → 两响应 isoformat 不等；`order_by(created_at.desc())` 同秒并列 run 非确定性收敛（可能停错 run）；seed 小数秒进 DATETIME(0) 被四舍五入跨秒边界 → web 秒精度过滤误含。

**修复全部沿用 06B 缺陷3/M-1 定论**（change-detection：业务字段真实变化才 bump；时间戳截断到存储精度），**未削弱任何断言**。
