### R2-01 / HIGH：空库升级证据未覆盖已有库增量升级，实际新表分支报 1101

- **位置**：[20261008_02_ingest_config.py:39](/home/wang/work/rosbag-catalog/alembic/versions/20261008_02_ingest_config.py:39)，TEXT 默认值在 47～49、72 行；起始迁移 [20260911_01_pipeline.py:14](/home/wang/work/rosbag-catalog/alembic/versions/20260911_01_pipeline.py:14)。
- **触发**：已有数据库升级至该迁移，尚不存在 ingest_profile/ingest_submission。`op.create_table` 对 TEXT 下发 `DEFAULT '[]'` 或 `'{}'`，MySQL 8.4 拒绝。
- **证据**：E-R2-MYSQL 使用真实 MigrationContext/Operations 执行实际迁移函数，捕获实际下发 DDL，服务端返回 **1101**。没有用 literal_binds 静态编译替代运行。
- **为什么与包内 E1 不矛盾**：空库从 base 开始时，起始迁移导入**当前** ORM 并 `create_all`，提前创建新表；02 的 `_table_exists` 使相应创建分支跳过。当前 ORM TEXT 只有 Python default，因此 general_log 中没有 DB DEFAULT。E1 证明空库路径成功，不能证明 02 新表创建分支合法；“MySQL 方言会省略 create_table 默认值”的解释不成立。
- **后果**：已有库上线迁移失败，不能启用本链路。空库成功不消除此风险。
- **最小修复**：修正 TEXT 默认值为 MySQL 支持的表达式默认值，或取消数据库 TEXT 默认值并保持所有写入显式赋值；按迁移发布策略处理已应用实例，避免无依据重写历史状态。
- **需补验证**：在真实旧 schema 的隔离副本上执行 `20261008_01→head`，确认迁移和实际 DDL；保留空库 upgrade 验证，两条路径分别报告。
- **门禁**：阻断 R2A 迁移接受、已有库升级/生产启用。对此前“#1 为误报”应收窄为“空库路径未失败”，不能维持全面排除。

### R2-02 / HIGH：MySQL outbox 查询读到字段名常量，事件永久留在 PENDING

- **位置**：[scene_schedule_consumer.py:57](/home/wang/work/rosbag-catalog/app/services/scene_schedule_consumer.py:57)。
- **触发**：MySQL 默认 SQL mode 没有 ANSI_QUOTES；`SELECT "event_id", "purpose", ...` 投影字符串常量，而非列。
- **证据**：E-R2-MYSQL 调用实际 `poll_outbox_events` 得到 `event_id='event_id'、purpose='purpose'`。随后实际 consumer 返回 `dropped=1, errors=[]`，却用常量 event_id 更新零行，真实事件仍为 **PENDING**。
- **后果**：正常事件被当未知用途处理，队列无法前进，头部 LIMIT 50 持续占位；统计还会误报已处理。违反 I1/I3，SQLite 用例隐藏差异。
- **最小修复**：用 SQLAlchemy Core 的列对象生成 SELECT，或使用方言正确的标识符引用；终态更新检查真实 event_id/影响行数，不能以计数替代持久化结果。
- **需补验证**：默认 sql_mode 的 MySQL 真实 bind→poll→consume，含正确 scene、自建、50 条坏事件及尾部正常事件；检查 DB 终态和建 run，不仅检查返回 stats。
- **门禁**：阻断 R2A MySQL 接收/调度集成及后续闭环。
