## 契约裁决（R2-05 跨 owner，两端同一策略）
**所有 scene run 在创建时（事件消费 或 显式 API）即分配并绑定 SceneAnalysisVersion 行；
换版比较用该行的提交时点顺序（持久序号/created_at at commit），不用回报时点。**
自动路径与显式路径统一——这样"晚到旧任务"不会再按回报先后覆盖"用户新分析"。
1号负责 create 侧（create_scene_run + consumer 建 run 时分配），2号负责 switch 侧（比较用提交序号）。
同一次客户端请求重试必须复用同一 reanalysis_id（强模型 Q1 已接受）。

## 门禁事实纠正（协调者自检，如实）
1. **06B 已于 09:07 由心跳化身合入（2e674b2）**，非审查包所写"暂停"。B8 OCR 四连败（会话中断
   杀后台进程）未收口期间，化身按"OCR 缺失→机械核验通过即合入"prompt 执行了合入——对一个
   **从未 OCR、从未强审的 fresh 模块**，这条 prompt 是错的。强模型明确"不指示回退已合入代码"，
   按返修处置；但**修正化身 prompt**：fresh 模块（无 OCR 收口记录 + 有 pending 强审包）禁止机械合入，
   只能挂 NEEDS_MAIN_REVIEW。
2. **03B/05/06A 的"DONE"是 SQLite 口径**：outbox 6/6 联调、各聚合复验、backfill 全在 SQLite 跑，
   SQLite 把双引号当标识符/允许自引用 UPDATE，系统性遮住 MySQL 方言坑（R2-02/03/01）。
   这些模块的 MySQL 生产路径**未完成验收**，05/03B 聚合从 DONE 退回 REWORK（MySQL 项），06A switch 标注跨模块阻断。
   教训：**凡涉及裸 SQL / 方言敏感 UPDATE 的代码，SQLite 全绿不构成 MySQL 放行证据**——
   我记忆里早有"T-03/T-04 MySQL 8.4 DDL 坑只在部署时暴露"，这次没把它推广到 DML/方言语法。
